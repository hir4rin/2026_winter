ステージはユーザーが自分で作る方針になったので、Unity に Window > Cyber Stage Palette を作った。アセットを日本語の分類・サムネイル・検索・お気に入りで置ける。ゲーム用の部品(床・壁走りの壁・縦穴・明かり・街灯・敵・エリアなど)はボタンで置ける。使い方は tools/CyberStage/自分で作るときの使い方.md。当たり判定は見た目の物の子なので、見た目を動かすと一緒に付いてくる。

3. 壁走りから次の壁へ張り付けなかったバグ

連続壁走りを置いても、ゲームでは蹴った後に次の壁へ一度も張り付けなかった。原因は条件の数字。

あわせて落下中(PlayerStateFall)でも、壁走りゾーンの壁に当たってスティックを倒していれば壁走りへ移れるようにした。蹴った勢いの上昇は10フレームで終わるので、次の壁に届くのは落下中になるため。

4. ステージの明かり ― 3回作り直した話

「Unity で置いた明かりで、ゲームの中の床・壁・キャラを本当に照らす」のが目的。3つのやり方を試した。

やり方結果
案ADxLib の標準のライト(CreatePointLightHandle)ダメ ほとんど明るくならない
案Bいつも通り描いた上に、光だけをもう1回加算で描く(重ね描き)ダメ 床がちかちか → 直そうとして後ろが透けた
案C(今)いつもの光と明かりを1回でまとめて計算する自作シェーダー採用 ずれが原理的に起きない 未確認

4-1. 案A がダメだった理由

このゲームのモデルは「拡散 0.1・環境光 0.9」にしてある(ライトの向きで明るさが変わりすぎないように)。DxLib のライトの明るさは ライトの色 × 材質の拡散 で、しかも合計が 1 で頭打ちになる。

4-2. 案B(重ね描き)で起きた2つの問題

案B は「① いつも通り描く ② 同じモデルを光だけのシェーダーでもう1回、加算で描く」というやり方。見た目を変えずに光だけ足せる……はずだった。

学んだこと: 同じ物を2回描いて重ねるなら、2回とも全く同じ計算で深さを出さないといけない。DxLib 標準の頂点シェーダーと自作のものは、数学的には同じでも細かい計算順が違って、ほんの少しずれる。ずらしで隠すと別の物が見えてしまう。→ そもそも2回描かないのが正解。

4-3. 案C:1回でまとめて描く

テスト用のプログラム(preview_lit)で確かめたこと:

  • 明かりが無いとき、DxLib の標準の描画とほぼ同じ見た目(平均の差 2.5 / 765)
  • 同じ絵を2回描いても差がゼロ(ちかちかしない)
  • 縦穴の壁にオレンジの光が乗る。Draw:Stage は CPU で約 0.15ms

7. カクつき対策

7-1. まず測った(FrameProfiler)

1フレームのどこに時間がかかっているかを測る道具を作った。

起動の引数に -bench を付けると、ステージ1にそのまま入って11秒動かして終わる(毎回同じ条件で測れる)。

7-2. 本当の原因:画面に出すタイミングのずれ

このPC(RTX 4060・モニター59Hz)では ScreenFlip の VSync 待ちが効いていなかった。前は自前の待ちだけで回っていて、1フレームが 16.70ms。モニターは 16.67ms なので少しずつずれていく。

  • モニターが 58〜62Hz なら WaitVSync(1) → ScreenFlip。それ以外(120/144Hz など)は今まで通り自前の待ち。
  • 確認用に -pace=busy / both / wait / dwm で待ち方を切り替えられる。dwm(Windows の画面の合成を待つ)も試したが WaitVSync とほぼ同じだったので、既定は WaitVSync のまま。
  • 測った結果: 間隔 平均 16.68ms・最短約14.5・最長約19ms、33ms のフレーム(飛び)は無し。

7-3. ついでに軽くしたこと

  • ステージを2回描くのをやめた(4-3 の LitModelPS)。GPU の負担が半分近くになる。
  • 毎フレーム配列を作り直していたのをやめ、使い回すようにした(StageLights の m_nearBuffer / m_paramBuffer など)。
